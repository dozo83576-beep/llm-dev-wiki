# Motion / UI-анимации

## Назначение

Документ задаёт production-правила для анимаций интерфейса: когда анимировать, какие
длительности и easing брать, как не уронить performance и доступность. Цель — анимация как
функция (feedback, пространственная связность, индикация состояния), а не как декор. Это
конспект принципов Emil Kowalski (Sonner / Vaul, курс «Animations on the Web»), адаптированный
под наш стек (React + CSS, опц. Motion/Framer Motion). Полный источник — в разделе «Источники»;
здесь — выжимка для принятия решений, не копия курса.

## Когда использовать

- Лендинги и продающие страницы: один оркестрированный page-load, hover-состояния, reveal.
- Продуктовый UI: модалки, drawer, тосты, поповеры, переключатели состояний.
- Жесты: swipe-to-dismiss, drag с инерцией, интерактив с мышью.

## Когда не использовать

- **Частые, клавиатурой-инициированные действия** (command palette, шорткаты, открытие по hotkey) —
  не анимировать вообще. Анимация на действии, которое происходит сотни раз в день, читается как
  тормоза. Эталон — Raycast open/close без анимации.
- Действия, повторяющиеся десятки раз в день (hover в плотных списках) — убрать или резко урезать.
- Внутренние плотные дашборды/админки, где важнее скорость и плотность данных — анимация
  минимальная и быстрая.

Правило частоты: чем чаще пользователь видит действие, тем меньше анимации оно заслуживает.
Delight-анимации — только для редких/первых событий (онбординг, празднование).

## Production-паттерны

### 1. Длительности (потолок UI — 300ms)

| Элемент | Длительность |
|---|---|
| Нажатие кнопки (feedback) | 100–160ms |
| Тултипы, мелкие поповеры | 125–200ms |
| Дропдауны, селекты | 150–250ms |
| Модалки, drawer | 200–500ms |
| Маркетинг/объясняющие | можно длиннее |

UI-анимации держать < 300ms. ~180ms ощущается отзывчивее, чем 400ms. Воспринимаемая
производительность важнее фактической: мгновенное движение в начале (через `ease-out`) усиливает
ощущение скорости.

### 2. Easing

- Вход/выход элемента → `ease-out` (стартует быстро, ощущается отзывчиво).
- Движение/морфинг на экране → `ease-in-out`.
- Hover / смена цвета → `ease`.
- Постоянное движение (marquee, прогресс) → `linear`.
- **Никогда `ease-in` для UI** — стартует медленно ровно в момент, на который смотрит пользователь.

Готовые кривые (не выдумывать свои; см. easing.dev):
```css
--ease-out:    cubic-bezier(0.23, 1, 0.32, 1);
--ease-in-out: cubic-bezier(0.77, 0, 0.175, 1);
--ease-drawer: cubic-bezier(0.32, 0.72, 0, 1);
```

### 3. Анимировать только `transform` и `opacity`

Эти свойства идут на GPU, минуя layout и paint. Анимация `width/height/margin/padding/top/left`
триггерит reflow и бьёт по INP/LCP. Перемещение — через `translate` (проценты относительно
размера самого элемента: `translateY(100%)` адаптивно). Масштаб дочерних — через `scale()`.

### 4. Кнопки и вход элементов

- Кнопка ощущается живой: `transform: scale(0.97)` на `:active`, transition `~160ms ease-out`
  (диапазон 0.95–0.98).
- Никогда не анимировать вход из `scale(0)` — ничего не появляется из небытия. Старт со
  `scale(0.9–0.95)` + `opacity: 0`.
- Поповеры масштабировать от триггера (`transform-origin` по CSS-переменной Radix/Base UI), модалки —
  остаются от центра.

### 5. Transitions vs keyframes; @starting-style

- Для часто-перезапускаемого/прерываемого UI (тосты, переключения) — CSS `transition`: его можно
  перенацелить на лету. `@keyframes` рестартятся с нуля.
- Вход без JS — через `@starting-style` (где поддержка позволяет), иначе паттерн `data-mounted`.
- Springs — для drag с инерцией и прерываемых жестов (сохраняют velocity). Bounce 0.1–0.3, экономно.

### 6. Stagger

При одновременном входе нескольких элементов — каскад с задержкой 30–80ms между элементами
(длинные задержки → ощущение тормозов). Stagger декоративен — не блокировать им интеракцию.

## Частые ошибки

- `transition: all` — указывать конкретные свойства (`transform 200ms ease-out`).
- `ease-in` на UI; длительность > 300ms на UI-элементе.
- Вход из `scale(0)`; `transform-origin: center` на поповере (кроме модалок).
- Анимация на клавиатурном/частом действии.
- Hover-анимация без `@media (hover: hover) and (pointer: fine)` — на тач ломается ложным hover.
- Одинаковая скорость входа и выхода — выход должен быть быстрее (медленно там, где решает
  пользователь; быстро там, где отвечает система).
- В Framer Motion shorthand `x/y/scale` НЕ hardware-accelerated (rAF на main thread) — под нагрузкой
  дропает кадры; использовать полный `transform: "translateX()"` или CSS-анимацию.

## Security / performance risks

- Тяжёлые decorative/particle-анимации и большое число анимируемых элементов бьют по LCP/INP —
  контролировать вес (см. [Performance](Performance.md)).
- `blur()` дорогой (особенно Safari) — держать < 20px.
- Смена CSS-переменной на родителе пересчитывает стили всех детей — для drag обновлять `transform`
  на самом элементе, не переменную на контейнере.
- CSS-анимации идут off-main-thread и переживают загрузку страницы; JS-анимации — для динамики и
  прерываемости. Программный CSS — через WAAPI (`element.animate`).

## Testing strategy

- Slow-motion (2–5×) и покадровый просмотр (DevTools Animations): проверить синхронность
  opacity/transform/color, корректность `transform-origin`, плавность easing.
- Тач-жесты (drawer, swipe) — на реальном устройстве, не только в эмуляторе.
- Проверить `prefers-reduced-motion`: движение/позиционные анимации убраны, opacity/color для
  понятности оставлены (reduced ≠ ноль анимаций).
- Lighthouse: анимации не валят INP/LCP.

## Edge cases

- swipe-to-dismiss: помимо порога расстояния учитывать velocity (`|dist|/time`), порог ~0.11 —
  быстрый флик закрывает.
- На границах drag — демпфирование/трение, а не жёсткий стоп; мульти-тач игнорировать после старта.
- Комбинация opacity + height при входе/выходе в списках подбирается итеративно, формулы нет.
- Ревью анимаций «на свежую голову» на следующий день — глаз ловит то, что замылилось при разработке.
