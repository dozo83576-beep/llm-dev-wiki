# Claude Code best practices

Конспект официального руководства «Best practices for Claude Code»: как строить агентную работу вокруг главного ограничения — контекстного окна, закрывать петлю запускаемой верификацией и масштабироваться до параллельных сессий.

- Источник: <https://code.claude.com/docs/ru/best-practices> (EN: `/en/best-practices`). Проверено: 2026-07-07.
- Практики проверены внутренними командами Anthropic на разных кодовых базах; это отправные точки, а не догмы.

## Назначение

Правила ведения агентной сессии, общие для всех проектов: что делает автономную работу агента надёжной (верификация, контекст-дисциплина, планирование) и что её ломает (замусоренный контекст, «выглядит готовым» без проверки, раздутые инструкции).

## Когда использовать

- Любая агентная сессия в любом проекте — Claude Code, Codex и другие рантаймы: принципы переносимы.
- Настройка нового репозитория под агентную работу: CLAUDE.md/AGENTS.md, hooks, skills, permissions.
- Диагностика «агент буксует»: почти всегда причина — переполненный контекст или отсутствие запускаемой проверки.

## Когда не использовать

- Не как замена project-local правил: project-`AGENTS.md`, security policy и production runbook приоритетнее.
- Не как догма: в исследовательских задачах расплывчатый промпт и накопленный контекст бывают полезны (см. «Интуиция важнее догм»).

## Ограничение №1: контекстное окно

Контекст — это весь разговор: каждое сообщение, каждый прочитанный файл, каждый вывод команды. Одна сессия отладки съедает десятки тысяч токенов, а производительность LLM деградирует по мере заполнения окна: агент «забывает» ранние инструкции и чаще ошибается.

Следствия:

- Широкие исследования — субагентам: они читают файлы в собственном окне и возвращают в основную сессию только сводку.
- Скоуп исследования задавать узко; «поизучай X» без границ = сотни прочитанных файлов.
- `/clear` между несвязанными задачами; `/compact <что сохранить>` для управляемого сжатия; быстрые побочные вопросы — `/btw` (не попадают в историю).
- Держать промпт коротким: тип задачи, путь, цель, ограничения, критерии готовности (см. [Token-efficient agent workflow](Token-efficient-agent-workflow.md)).

## Верификация: дай агенту способ проверить свою работу

Ключевой принцип. Без проверки, которую агент может запустить, «выглядит готовым» — единственный сигнал остановки, и петлёй проверки становится человек. Проверка — всё, что возвращает читаемый сигнал: тесты, exit-код сборки, линтер, скрипт сравнения с фикстурой, скриншот против макета.

| Стратегия | Слабо | Сильно |
|---|---|---|
| Критерии проверки | «реализуй валидацию email» | «функция validateEmail; тест-кейсы: user@example.com→true, invalid→false, user@.com→false; запусти тесты после реализации» |
| Визуальная проверка UI | «сделай дашборд лучше» | «[скриншот] реализуй этот дизайн; сними скриншот результата, сравни с оригиналом, перечисли отличия и исправь» |
| Root cause, не симптом | «сборка не работает» | «сборка падает с ошибкой: [вставка]; исправь корневую причину, не подавляй ошибку, проверь что сборка зелёная» |

Лестница жёсткости (чем автономнее запуск, тем жёстче шлюз):

1. **В одном промпте** — «сделай + запусти проверку + итерируй до зелёного».
2. **На всю сессию** — `/goal`: отдельный оценщик перепроверяет условие после каждого хода.
3. **Детерминированный шлюз** — Stop hook запускает проверку скриптом и блокирует завершение хода (снимается после 8 блокировок подряд).
4. **Второе мнение** — verification-субагент со свежим контекстом пытается опровергнуть результат: исполнитель не оценивает сам себя.

**Доказательства, а не утверждения**: вывод теста, команда и что она вернула, скриншот результата. Проверить доказательство быстрее, чем перезапускать проверку самому, и это работает для сессий без наблюдения.

## Explore → Plan → Code → Commit

1. **Исследуй** (Plan Mode): агент читает файлы и отвечает на вопросы без изменений.
2. **Планируй**: подробный план реализации; план можно править в редакторе до продолжения (Ctrl+G).
3. **Реализуй** (выход из Plan Mode): кодирование со сверкой против плана + тесты.
4. **Зафиксируй**: коммит с описательным сообщением, PR.

Когда пропускать план: дифф описывается одним предложением (опечатка, строка логирования, переименование). Планирование ценно, когда подход неясен, изменение многофайловое или код незнаком.

## Конкретный контекст в промптах

| Стратегия | Слабо | Сильно |
|---|---|---|
| Скоуп задачи | «добавь тесты для foo.py» | «тест для foo.py на граничный случай разлогиненного пользователя; без моков» |
| Источник ответа | «почему у ExecutionFactory странный API?» | «пройди git-историю ExecutionFactory и суммируй, как API к этому пришёл» |
| Референс-паттерн | «добавь виджет календаря» | «посмотри, как реализованы виджеты на главной (HotDogWidget.php — образец), сделай календарь по тому же паттерну, без новых библиотек» |
| Симптом бага | «почини логин» | «после истечения сессии логин не работает; проверь src/auth/, особенно refresh токена; сначала красный тест-репродукция, потом фикс» |

Богатый контент: `@файл` вместо описания места; вставка скриншотов/изображений; URL на доки (частые домены — в whitelist); `cat error.log | claude`; «сам вытяни контекст» через bash/MCP. Расплывчатый промпт уместен в исследовании («что бы ты улучшил в этом файле?»).

## Настройка окружения

### Эффективный CLAUDE.md

- `/init` генерирует стартовый файл; читается каждую сессию → только широко применимое; редкое доменное знание — в skills (грузятся по требованию).
- Тест каждой строки: «привело бы удаление к ошибкам агента?» Нет — удалить. Раздутый файл = важные правила теряются в шуме, агент их игнорирует.
- ✅ Включать: команды, которые не угадать; отклонения от стандартов языка; тест-раннеры и предпочтения; этикет репозитория (ветки, PR); архитектурные решения проекта; env-требования; неочевидные подводные камни. ❌ Исключать: выводимое из кода; стандартные конвенции; длинные туториалы и API-доки (ссылаться); часто меняющееся; «пиши чистый код».
- Импорты: `@path/to/file` внутри CLAUDE.md. Уровни: `~/.claude/CLAUDE.md` (все сессии), `./CLAUDE.md` (в git, для команды), `./CLAUDE.local.md` (личное, в .gitignore), родительские (монорепо) и дочерние каталоги (по требованию).
- Если правило есть, а агент его нарушает — файл слишком длинный или формулировка неоднозначна. Относиться как к коду: ревизовать при сбоях, регулярно резать, проверять эффект изменений. Акцент «IMPORTANT»/«YOU MUST» усиливает соблюдение.

### Permissions, CLI, MCP, hooks, skills, субагенты

- **Permissions**: auto mode (модель-классификатор блокирует только рискованное), allowlist конкретных команд, sandbox (изоляция ОС) — меньше прерываний при сохранении контроля.
- **CLI-first**: `gh`, `aws`, `gcloud`, `sentry-cli` — самый контекстно-эффективный канал к внешним сервисам; незнакомый CLI: «запусти `foo --help`, изучи и реши A, B, C».
- **MCP**: трекеры, БД, Figma, мониторинг — подключить один раз вместо вставки данных в каждую сессию.
- **Hooks** — детерминированная гарантия (в отличие от рекомендательного CLAUDE.md); агент сам пишет hook по описанию триггера и действия.
- **Skills**: `SKILL.md` в `.claude/skills/` — доменные конвенции и повторяемые workflow; `disable-model-invocation: true` для workflow с побочными эффектами (только ручной запуск).
- **Субагенты**: `.claude/agents/*.md` — свой контекст и свой набор инструментов; для задач, читающих много файлов, и специализированного ревью.
- **Plugins**: `/plugin`; для типизированных языков — code intelligence (навигация по символам, ошибки после правок).

## Коммуникация

- Вопросы к кодовой базе — как senior-инженеру: «как работает логирование?», «какие edge cases обрабатывает X?» — эффективный онбординг без нагрузки на коллег.
- Крупная фича — интервью вместо самописной спеки: «I want to build X. Interview me in detail using the AskUserQuestion tool… then write a complete spec to SPEC.md». Реализация — в свежей сессии с чистым контекстом. Хорошая спека самодостаточна: файлы и интерфейсы, что вне скоупа, финальная сквозная проверка.

## Управление сессией

- **Ранняя коррекция**: `Esc` — стоп посреди действия (контекст цел); `Esc×2`/`/rewind` — откат разговора и/или кода к контрольной точке; «undo that»; `/clear` между несвязанными задачами.
- **Правило двух фиксов**: две неудачные попытки одной проблемы = контекст замусорен неудачными подходами → стоп, новый заход/чистая сессия с промптом, включающим выученные ограничения. Чистая сессия с лучшим промптом почти всегда бьёт длинную с накопленными исправлениями.
- **Компактирование**: `/compact <указания>`; в CLAUDE.md можно задать, что сохранять при сжатии (список файлов, тест-команды); частичное сжатие — rewind → «Summarize from/up to here».
- **Checkpoints**: снапшоты файлов перед каждым изменением; позволяют смелые эксперименты с откатом; живут между сессиями; НЕ замена git (внешние процессы не отслеживаются).
- **Resume**: `claude --continue` / `--resume`; сессии именовать (`/rename`, напр. `oauth-migration`) и вести как ветки — по постоянному контексту на рабочий поток.

## Масштабирование

- **Headless**: `claude -p "…"` в CI, pre-commit, скриптах; `--output-format json|stream-json` для программного разбора.
- **Параллельные сессии**: worktrees (изолированные checkouts), desktop app, web (облачные VM), agent teams (координация с общими задачами).
- **Writer/Reviewer**: одна сессия пишет, вторая ревьюит — свежий контекст не предвзят к только что написанному коду; аналогично «один пишет тесты, другой — код под них».
- **Fan-out**: список задач → цикл `claude -p` на каждую с `--allowedTools` (ограничение прав обязательно для запусков без присмотра); промпт отладить на 2–3 файлах, потом гнать весь набор.
- **Auto mode**: `claude --permission-mode auto -p "…"` — классификатор проверяет команды в фоне; в headless при повторных блокировках запуск прерывается.
- **Состязательное ревью**: перед «готово» — субагент со свежим контекстом сверяет дифф с планом: «каждое требование реализовано, перечисленные edge cases покрыты тестами, ничего вне скоупа не изменено; сообщай пробелы, не стилистику». Осторожно: ревьюер, которого просят найти пробелы, найдёт их всегда — принимать только влияющее на корректность/требования, иначе оверинжиниринг (лишние абстракции, оборонительный код, тесты невозможных случаев).

## Частые ошибки

- **Kitchen-sink-сессия**: несвязанные задачи в одном контексте → `/clear` между задачами.
- **Фикс за фиксом**: после двух неудачных исправлений → `/clear` + лучший стартовый промпт с выученным.
- **Раздутый CLAUDE.md**: правила теряются в шуме → безжалостно резать; то, что агент и так делает, — удалить или превратить в hook.
- **Доверие без проверки**: правдоподобная реализация без обработки edge cases → всегда давать проверку; нельзя проверить — нельзя отправлять.
- **Бесконечное исследование**: «поисследуй» без скоупа заполняет контекст → узкие рамки или субагенты.

## Интуиция важнее догм

Паттерны — отправные точки. Иногда контекст нужно копить (глубокая отладка одной проблемы), иногда план пропускать (исследовательская задача), иногда расплывчатость полезна (увидеть интерпретацию агента до сужения). Замечать, что сработало: структуру промпта, предоставленный контекст, режим — и почему агент буксовал (шумный контекст? расплывчатый промпт? слишком крупная задача?).

## Проверка

Перед завершением значимой задачи: (1) существует запускаемая проверка и её вывод показан; (2) крупный дифф прошёл ревью в свежем контексте против плана; (3) широкие исследования шли через субагентов, а не раздували основную сессию; (4) причины решений зафиксированы (план/коммит/learning review).
