# WooCommerce marketplace order split

Мультивендорная корзина → один заказ WooCommerce и один платёж → автоматическая разбивка на суб-заказы по продавцам как **бухгалтерская проекция**, без сплит-платежей на стороне эквайринга. Референс: `local-market-woo` ([case study](../../case-studies/successes/2026-07-02-local-market-woo-woocommerce-marketplace.md)).

## Когда использовать

Маркетплейс на WooCommerce с выплатами продавцам через реестр/ручной экспорт (без Connect-класс сплита). Нужны: per-vendor суммы, комиссия, статистика продавца, изоляция данных.

## Когда не использовать

Если требуются настоящие сплит-платежи на чекауте (деньги сразу разъезжаются по продавцам) — это интеграция уровня эквайринга (Stripe Connect / ЮKassa-магазины), суб-заказы её не заменяют.

## Production-паттерны

- **Точка входа** — хук `woocommerce_checkout_order_processed`: сгруппировать `$order->get_items()` по `vendor_id` (postmeta товара), на каждую группу — строка в кастомной таблице суб-заказов + строки позиций.
- **Идемпотентность**: метка `_split_done` в мета заказа — хук может сработать повторно (ретраи/дубли запросов).
- **Комиссия резолвится по приоритету** (товар → продавец → категория → глобальный дефолт) одной функцией, используемой и на чекауте, и в превью «сколько заработаю» в кабинете; строка-снапшот ставки (`percent:10`) пишется в суб-заказ — историю не пересчитывать.
- **Статусы суб-заказов — проекция родителя**: `woocommerce_order_status_changed` мапит статус родителя на все суб-заказы; отдельного жизненного цикла у суб-заказа нет, потому что платёж один.
- **Леджер выплат**: на `completed` — credit-строка с `eligible_at = completed + hold-период` (окно возвратов); на `woocommerce_order_refunded` — компенсирующий debit пропорционально возвращённой доле. Экспорт помечает строки `exported` общим `batch_id` — защита от двойной выплаты.
- **Изоляция продавцов**: `vendor_id` играет роль tenant_id — каждый запрос кабинета фильтрует по нему; обязательны negative-тесты (продавец A получает 403/404 на ресурсы продавца B).

## Частые ошибки

- Разбивать заказ на настоящие дочерние `shop_order` — усложняет платежи/возвраты; проекция в своей таблице проще и безопаснее.
- Считать комиссию один раз на всю корзину продавца — ставки могут различаться по товарам; резолвить per-line, суммировать.
- Списывать возврат с продавца по «сырой» сумме возврата, а не пропорционально его payout-доле.

## Проверка

Интеграционные тесты (wp eval-file против живого WC): корзина 2+ продавцов → корректное число суб-заказов и суммы по каждому уровню комиссии; повторный вызов хука не создаёт дублей; возврат создаёт debit; vendor-scoped запрос не видит чужих строк.
