# Lesson: делегирование фото-сорсинга субагенту — взрыв tool calls без результата

## TL;DR

Delegating "search Pexels, verify N candidates, download M photos" to a general-purpose subagent
with only browser tools risks a tool-call explosion (heavy `browser_snapshot`/screenshot per
candidate) that can burn the whole task budget and return **zero files**, with a report that can't
be trusted if the safety classifier was unavailable for that run. Doing the same task directly with
a DOM-`evaluate`-first workflow finished all 11 photos in a fraction of the calls.

## Контекст

Ревизия лендинга (Astro 7 + Tailwind v4, премиальный beauty-сайт) по фидбеку клиента: нужно было
подобрать и скачать 11 новых stock-фото с Pexels под конкретные карточки, с обязательной визуальной
проверкой внешности модели (см. [Проверка stock-фото](../patterns/frontend/stock-photo-id-verification.md)).

## Что произошло

Задача была делегирована фоновому `general-purpose` агенту с подробным брифом (11 позиций, критерии
отбора, workflow через Playwright). Агент отработал **119 tool calls за ~23 минуты** и не сохранил ни
одного файла — проверка `public/img/` до и после показала одинаковый список из 18 старых файлов, ни
одного нового. Финальный "результат" агента не был отчётом по задаче, а системным уведомлением:
классификатор безопасности (`claude-sonnet-5`) был недоступен для ревью этого запуска, плюс отметка о
достижении лимита сессии. То есть агент либо застрял в цикле поиска/сравнения кандидатов, либо упёрся
в лимит раньше, чем успел что-то скачать — и без независимого ревью его промежуточным заявлениям
доверять было нельзя в принципе.

Задача была переделана напрямую (не в субагенте) с другим workflow:
1. `browser_evaluate` на странице поиска Pexels: `document.querySelectorAll('img[src*="images.pexels.com/photos"]')`
   → src+alt всех миниатюр одним вызовом (несколько KB текста).
2. Один `browser_navigate` на страницу кандидата + **один** `browser_take_screenshot` — только для
   финальной визуальной проверки (композиция, этничность, не слишком тесный кроп чтобы лицо было видно).
3. Если кандидат не подходит (лицо не той внешности, слишком tight crop, лицо закрыто руками,
   слишком откровенно для клиентского сайта, композиция дублирует уже выбранное фото) — вернуться к
   шагу 2 с другим кандидатом, без повторного полного поиска.
4. Прямое скачивание оригинала через `Invoke-WebRequest`/`curl` по CDN-URL
   (`https://images.pexels.com/photos/<id>/pexels-photo-<id>.jpeg?auto=compress&cs=tinysrgb&w=1600`,
   либо с собственным slug-сегментом фото для новых ID) — без похода в Pexels UI за кнопкой "Free
   download".

Итог: все 11 фото подобраны (несколько кандидатов отклонены по ходу: не та внешность, лицо не видно,
дубль по композиции, "topless"-заголовок неуместен для premium клиентского сайта), скачаны, размер
файлов подтверждён (не 0 байт) — примерно за 4-6 tool calls на фото, без единого `browser_snapshot`
результатов поиска и без полностраничных скриншотов галереи кандидатов.

## Корень

`browser_snapshot` без ограничения глубины на странице результатов поиска возвращает 60k+ символов
(сам инструмент это подтвердил, потребовав сохранения в файл) — то есть один-единственный "посмотреть
что в выдаче" стоит как десятки обычных вызовов. Полноразмерный `browser_take_screenshot` на каждого
из нескольких кандидатов на позицию (а не только на финально выбранного) умножает это ещё на N. При
11 позициях и осторожном переборе 2-3 кандидатов на каждую это быстро уходит за сотню вызовов —
и субагент, у которого нет обратной связи о собственном "бюджете", не видит сигнала остановиться и
попробовать более дешёвый путь.

## Новое правило

Когда задача = «пересмотреть N stock-фото кандидатов и скачать M из них» → **сначала `evaluate`,
скриншот только на кандидате, которого уже почти выбрал, скачивание напрямую по CDN-URL** — не
делегировать это в субагента, который единственный доступный путь видит через
`browser_snapshot`/`browser_take_screenshot` на каждом шаге. Если объём (много десятков фото) всё же
требует делегирования — явно прописать в брифе субагента именно этот дешёвый workflow (не просто
"используй Playwright"), и после его возврата **всегда** проверять результат независимо от
самоотчёта (`ls`/`Glob` на ожидаемые пути), особенно если ответ агента не похож на предметный отчёт
по задаче (короткое системное сообщение вместо таблицы с результатами — сигнал не доверять и
перепроверить с нуля).

## Применимость

Применимо к любой задаче с браузерным перебором визуальных кандидатов (stock-фото, иконки, референсы
дизайна) под сорсинг для сайта. Не применимо к задачам, где нужен ровно один просмотр страницы без
перебора кандидатов (там `browser_snapshot`/`screenshot` разумны и дёшевы за один вызов).
