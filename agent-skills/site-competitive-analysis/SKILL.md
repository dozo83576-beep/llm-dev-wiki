# site-competitive-analysis — конкурентный анализ и адаптация

Тонкий роутер. Источник правды по методу — `D:\Work\llm-dev-wiki`. Цель: понять, «как выглядит хороший сайт
этого продукта», и превратить это в **оригинальный** план под конкретный бриф, а не в копию конкурента.

## Requires
- `site-discovery` завершён: есть тип продукта и бриф (иначе вернись в discovery, не угадывай конкурентов).

## Когда использовать
- После `site-discovery`, когда есть тип продукта и бриф; перед `site-architecture`.
- Когда в ТЗ просят «посмотреть конкурентов / взять лучшее с похожих сайтов».

## Когда НЕ использовать / граница
- Не копировать вёрстку, тексты, изображения, шрифты-как-набор, логотипы или бренд конкурента — это
  copyright/trademark риск и путь к дженерику. Извлекаем **паттерны и принципы**, синтез оригинальный.
- Если тип продукта неясен — сначала вернись в `site-discovery`, не угадывай конкурентов.

## Слои контекста
1. Project-local `AGENTS.md` → `D:\Work\AGENTS.md` → `D:\Work\AGENT-PREFERENCES.local.md` → вики.
2. Бриф и ответы интервью из `site-discovery` — это фильтр, по которому отбирается «лучшее».

## Сначала прочитай
- `D:\Work\llm-dev-wiki\docs\01-development-process\competitive-analysis.md` — метод, таксономия извлечения,
  граница «что не копировать», output schema финального плана и чеклист.
- `D:\Work\llm-dev-wiki\docs\07-mcp-and-ai-tools\External-site-skills.md` — optional helpers
  `competitive-intel`, `competitive-teardown`, `competitor-alternatives`, если они установлены.
- `D:\Work\AGENT-PREFERENCES.local.md` — одобренные предпочтения (учесть при отборе «лучшего»).

## Шаги
1. **Тип продукта.** Возьми продукт из запроса/брифа (например «массажный салон в Екатеринбурге»).
2. **Найди конкурентов.** Через `WebSearch` подбери 5–6 сайтов того же продукта, высоко котируемых в выдаче /
   известных. Зафиксируй список URL и почему именно они (релевантность, видимость). Опц. `similarweb`/`ahrefs`
   коннекторы для сигналов трафика/ранга, если подключены.
2.5. Если доступны внешние helpers для competitors, используй максимум 1-2 как дополнительный анализ, не как замену
   WebSearch/WebFetch и собственного синтеза.
3. **Извлеки на каждом** (через `WebFetch`, только публичные страницы):
   - Структура страниц (главная, услуги, цены, запись/бронь, о нас, отзывы, контакты, блог).
   - Навигация / информационная архитектура (меню, группировка, глубина).
   - UX-паттерны (флоу записи/заявки, расположение CTA, формы, trust-сигналы, карты, мессенджеры).
   - Контент-углы (заголовки, ценностные сообщения, FAQ, SEO-темы).
   - Фичи (онлайн-запись, прайс-лист, сертификаты, акции/лояльность, отзывы, мультиязычность).
4. **Тех-бенчмарк** публичных страниц конкурентов:
   `pwsh D:\Work\llm-dev-wiki\tools\site-audit.ps1 -Url <конкурент> -Routes /,/services,/contacts`
   — Lighthouse perf/SEO/a11y/best-practices. Это планка, которую наш сайт должен побить.
5. **Синтез.** Сведи в матрицу «фичи/паттерны × конкуренты». Раздели на **table-stakes** (есть у большинства —
   обязательны) и **дифференциаторы** (редкие — возможность выделиться).
6. **Адаптация под бриф.** Прогони каждый паттерн через фильтр интервью (цель, аудитория, бюджет, сроки,
   constraints). Явно реши: что берём и почему, что не берём. Приоритизируй **must / should / could**.
7. **Окончательный план сайта.** Выдай: sitemap/страницы, навигацию, ключевые UX-флоу, контент-аутлайн по
   страницам, список фич с приоритетом и измеримые цели «побить» тех-метрики конкурентов.
8. **Артефакт.** Сохрани анализ и план в папку проекта как `_competitive-analysis.md` (URL конкурентов
   приватны — не в вики).

## Quality gate
- 5–6 релевантных конкурентов с обоснованием выбора; у каждого извлечены структура, навигация, UX, контент, фичи.
- Есть тех-бенчмарк (числа Lighthouse), из него выведены наши целевые пороги.
- Финальный план адаптирован под бриф (видно «взяли/не взяли и почему»), фичи приоритизированы must/should/could.
- Нет скопированных чужих текстов/вёрстки/бренда — только оригинальный синтез.
- Проверяет: self-check агента + тех-бенчмарк через `site-audit.ps1` (tool).
