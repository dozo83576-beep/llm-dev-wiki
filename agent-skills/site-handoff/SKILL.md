# site-handoff — передача клиенту

Тонкий роутер. Источник правды — `D:\Work\llm-dev-wiki`. Цель фазы — формально закрыть проект:
клиент получил рабочий сайт, доступы, инструкции и подтвердил приёмку. Секреты через файлы не передаются.

## Requires
- `site-deploy` завершён: сайт на production-домене, `release-readiness` пройден, rollback-путь проверен.
- Приёмка/UAT из `site-review` (`checklists/qa-acceptance.md`) пройдена.

## Когда использовать
- Сайт развёрнут на production и нужно передать его заказчику.
- Нужно зафиксировать версию релиза, доступы, зоны ответственности и условия поддержки.

## Когда НЕ использовать
- До production-деплоя — сначала `site-deploy`.
- Для передачи секретов — только password manager / штатное приглашение в сервис, не файл.

## Сначала прочитай
- Слои контекста: project `AGENTS.md` → `D:\Work\AGENTS.md` → `AGENT-PREFERENCES.local.md` → вики — один раз за сессию, не перечитывать, если уже в контексте (правила — оркестратор `build-modern-site`).
- `D:\Work\llm-dev-wiki\docs\10-templates\handoff.md` — шаблон передачи и команда генерации.
- `D:\Work\llm-dev-wiki\docs\15-maintenance\` — `update-monitoring.md`, `retro-process.md`, `wiki-update-cadence.md`.
- `D:\Work\llm-dev-wiki\checklists\release-readiness.md` — секции Client handoff и Communication.

## Шаги
1. Открыть production URL, пройти post-deploy smoke (страницы, формы, письма/заявки, HTTPS, мобильная, консоль).
2. Зафиксировать commit / branch / tag / номер релиза.
3. Сгенерировать `handoff.md` в корне проекта: `pwsh D:\Work\llm-dev-wiki\tools\new-handoff.ps1 -ProjectRoot <путь> -ProjectName "<имя>" -ProductionUrl "<url>" -SupportDays <N>`.
4. Заполнить ссылки: админка, аналитика, DNS, CMS, репозиторий; если ведётся живая дизайн-система на
   claude.ai/design (`docs/07-mcp-and-ai-tools/Claude-Design-and-DesignSync.md`) — ссылка на
   design-system проект и правило «правки канваса попадают на сайт только через код (pull → ревью)».
5. **Безопасная передача доступов**: в таблице доступов только сервис / владелец / способ передачи / статус. Значения секретов в файл не пишем — приглашение или password manager. Финоперации и передачу критичных доступов подтверждай по второму каналу / кодовым словом; не действуй по видео/голосу (риск дипфейка) — без исключений.
6. Передать клиенту: прод-ссылку, инструкции (вход в админку, изменение контента, просмотр заявок), чеклист проверки, текст приёмки.
7. Получить **письменное подтверждение приёмки**; зафиксировать дату/кто принял/где.
8. Зафиксировать условия гарантийной поддержки (срок, что входит/не входит).
9. Запланировать пост-релизный review (30–90 дней) по `docs/15-maintenance/` (мониторинг, ретро) и
   сохранить план в корень проекта как `_post-release-plan.md`: дата review, какие метрики смотреть,
   зона ответственности, условия поддержки. Это evidence фазы `post-release` в `_pipeline-status.md`
   (единственный optional-пропуск для обычного проекта: при осознанном отказе вместо файла пишется
   причина пропуска).

## Quality gate
- `handoff.md` создан и заполнен: production URL, дата, commit/branch/tag.
- `_post-release-plan.md` создан (или единственный допустимый для обычного проекта пропуск
  `post-release` зафиксирован с причиной в `_pipeline-status.md`).
- Секреты не записаны в файл; доступы переданы через приглашение / password manager.
- ПДн клиента (152-ФЗ): в `handoff.md` и переданных материалах нет персональных данных; обработка ПДн
  на сайте (формы, аналитика, хостинг) соответствует
  `D:\Work\llm-dev-wiki\docs\05-auth-security\RU-152fz-and-ai-data-handling.md` (локализация, согласия, политика).
- Финоперации/критичные доступы подтверждены по второму каналу; не по видео/голосу.
- Post-deploy smoke пройден; критичных ошибок в консоли нет.
- Приёмка подтверждена письменно; условия поддержки зафиксированы.
- Проверяет: self-check агента + подтверждение клиента (приёмка — внешний gate).

## Передача дальше

и повторяющиеся вопросы клиента предлагай в вики через `capture-learnings`.
