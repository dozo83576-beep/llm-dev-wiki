# site-discovery — фаза требований

Тонкий роутер. Источник правды — `D:\Work\llm-dev-wiki`.

## Requires
- Точка входа цикла: предусловий нет. Принимает raw request (`Я хочу создать сайт <описание>`) или частичные требования.

## Когда использовать
- Старт нового сайта/веб-приложения; требования неполные.
- Перед `site-competitive-analysis`, `site-stack` и `site-architecture`.

## Сначала прочитай
- `D:\Work\llm-dev-wiki\checklists\project-discovery.md` — что обязательно выяснить.
- `D:\Work\llm-dev-wiki\prompts\discovery-interview.md` — как вести интервью.
- `D:\Work\llm-dev-wiki\docs\07-mcp-and-ai-tools\External-site-skills.md` — optional helpers
  `market-research`, `product-discovery`, `marketing-context`, если они установлены.
- `D:\Work\AGENT-PREFERENCES.local.md` — известные предпочтения, чтобы не переспрашивать.

## Шаги
1. Задавай только недостающие вопросы из чеклиста — один вопрос на блок, не вываливай всё сразу.
1.5. Если доступны релевантные external helpers, используй максимум 1-2 для исследования рынка/ICP; не заменяй ими
   checklist и не сохраняй их вывод как truth без проверки.
2. Зафиксируй тип продукта, аудиторию, роли, ключевые страницы/экраны, интеграции (платежи, email,
   AI, аналитика), сроки, hosting, auth, БД, бюджет, compliance.
2.5. Спроси про визуальные референсы клиента: есть ли сайты/скриншоты/примеры «вот так нравится —
   вот так не нравится»? Зафиксируй ссылки/файлы как `reference-pointers` даже без анализа на этом
   этапе — это прямой вход для `site-design`, который не должен переспрашивать заново. Пусто —
   зафиксируй явно «референсов нет».
3. Сформулируй измеримые acceptance criteria — сценарии, по которым видно, что проект готов.
4. Юрисдикция и ПДн: уточни аудиторию (РФ/EU) и какие персональные данные собираются. Для РФ-аудитории это триггерит 152-ФЗ (политика, согласие, локализация ПДн, уведомление Роскомнадзора — см. `docs/05-auth-security/RU-152fz-and-ai-data-handling.md`).
5. Отметь блокеры (особенно compliance/152-ФЗ) явно, не угадывай.
6. **Артефакт.** Сохрани зафиксированные требования в корень проекта как `_discovery.md`: тип
   продукта, аудитория, роли, страницы, интеграции, hosting/auth/БД, acceptance criteria,
   `reference-pointers`, юрисдикция/ПДн, открытые вопросы и блокеры. Это вход для
   `site-competitive-analysis`, `site-stack` и `site-architecture` — и точка resume после
   перезапуска сессии (в plan-режиме — материализуется сразу после одобрения плана, см. оркестратор).
   Если файл уже существует — актуализируй его, а не начинай интервью с нуля.

## Quality gate
- Есть тип проекта, роли, интеграции и ≥3 проверяемых acceptance criteria.
- `reference-pointers` зафиксированы явно (ссылки/файлы или явное «референсов нет»).
- Открытые вопросы и блокеры перечислены явно.
- Требования сохранены в `_discovery.md` проекта (или запланированы к материализации после
  одобрения плана).
- Проверяет: self-check по `project-discovery.md` + подтверждение требований заказчиком.

## Передача дальше
`site-competitive-analysis` — конкурентный анализ на основе зафиксированных требований (следующий
шаг перед выбором стека; `site-stack` требует его результат — не пропускать).
